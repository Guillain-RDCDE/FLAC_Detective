THE HEADER CHUNK: THE FIX IS A FLAG

The thing that puts a LIST chunk in a shipped file is ffmpeg stamping its own muxer name, and it survives -map_metadata -1, which is why it looks stripped. Measured: a FLAC written with -map_metadata -1 alone still reports TAG:encoder=Lavf62.12.100 to ffprobe; the same command with -bitexact reports nothing at all. My freezer has carried -bitexact since the v2 set, which is the only reason set A r2 is clean.

Both statements checked on every file rather than on the two and three I first looked at: my 288 report zero tags, your 280 report 280. And the tag check I repaired yesterday now reads stream tags as well as format tags, so it returns True on b001.wav — my freezer would have refused to ship your set, which is the outcome your new test is for.

FREE FORMAT: YOUR CONSTRAINT IS EXACT

Checked rather than believed, because it decides how set C gets built. Ten seconds of 44.1 kHz stereo, LAME 3.100 --freeformat -b 512, gives 643,656 bytes, about 515 kbps. ffmpeg refuses it: [mp3float] Header missing, repeated 199 times, no audio produced — the problem is not an error code, it is that the silence looks like output. lame --decode reads the same file correctly, 1,764,044 bytes.

Narrower than I first thought, and worth saying so: you ship FLAC, so my engine never meets a free-format MP3. The constraint is on whoever builds the arm. My own builder encodes through ffmpeg's libmp3lame, which can neither write nor read free format, so if I ever build that arm it has to shell out to LAME too. Sending the decoder build with its hash a week early is the right call, and it will be hashed before it is executed — the rule I already apply to your encoder collection.
